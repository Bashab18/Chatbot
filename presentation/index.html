BM25 Algorithm

BM25 — Why No Vector Embeddings?

BM25 Formula
score(D,Q) = Σ IDF(qᵢ) · [tf(qᵢ,D) · (k1+1)] / [tf(qᵢ,D) + k1 · (1-b+b·|D|/avgdl)]
Parameters: K1=1.5, B=0.75 (tuned for English prose)
Stopwords: 47 common English words filtered out
Output: Ranked list of chunk indices by relevance score
// BM25 constants in embed.js const K1 = 1.5; const B = 0.75; const STOPWORDS = new Set([ 'the', 'is', 'at', 'which', 'on', // ... 42 more ]);
BM25 vs. Vector Embeddings
AspectBM25Vector
API callsNonePer chunk
Storage~12MB SQLiteGBs (FAISS)
Latency<5ms50–200ms
Cost$0$$/million
ExplainabilityHighLow
Semantic searchKeywordSemantic
✅ For domain-specific documents, keyword search matches performance of semantic search at a fraction of the cost.

Multi-Instance

Multi-Instance Architecture

A single CIRA codebase can power multiple independent chatbot instances simultaneously, each with its own:

  • ▶Isolated SQLite database (users, conversations, KB)
  • ▶Unique TCP port (5000, 5001, 5002…)
  • ▶Separate data directory on disk
  • ▶Independent bot name and configuration
  • ▶Spawned by a single `start-instances.js` launcher
Use case: "CIRA A" for public users, "CIRA B" for internal staff — same codebase, different configs.
// instances.json [ { "name": "CIRA A", "port": 5000, "dataDir": "data/chatbot-a" }, { "name": "CIRA B", "port": 5001, "dataDir": "data/chatbot-b" } ] // start-instances.js spawns child processes for (const inst of instances) { spawn('node', ['server.js'], { env: { ...process.env, PORT: inst.port, INSTANCE_NAME: inst.name, DATA_DIR: inst.dataDir } }); }

RAG Pipeline

RAG Pipeline — Detailed Flow

Ingestion Phase (Document Upload)
1
Admin uploads PDF/TXT/MD file
Multer middleware handles multipart/form-data. 20MB limit enforced.
2
Text Extraction
PDF → pdf-parse extracts text. TXT/MD → read directly. Binary content stripped.
3
Chunking (400w / 60w overlap)
chunker.js splits text at sentence boundaries within 400-word windows. 60-word overlap preserves context continuity.
4
BM25 Tokenization → Store
embed.js tokenizes each chunk, removes stopwords, stores token array as JSON in kb_chunks table.
Retrieval Phase (Chat Query)
A
Tokenize user query
Same BM25 tokenizer applied to query string. Stopwords removed.
B
Score all KB chunks
BM25 IDF × TF formula scores each chunk against query tokens. O(n×k) where n=chunks, k=query terms.
C
Return Top-K (default K=5)
Highest-scored chunks with source document names returned. Appended to Gemini systemInstruction.
D
Citations in response
Source document names returned to client alongside AI response for transparency.

Error Handling

Error Handling & Fallback Flows

🔄
JSON Parse Fallback
If Gemini returns JSON wrapped in markdown fences, they are stripped before parse. On continued failure, system switches to Gemini 1.5 Flash in forced JSON mode.
📭
Empty KB Results
If KB-only mode is strict and BM25 finds no relevant chunks, CIRA returns a graceful "I don't have information on that in my knowledge base" message.
🌐
Web Search Disabled on Gemma
Gemma models don't support Google Search tool. If webSearchWeight > 0 and model is Gemma, web search is silently skipped. Admin warned in settings UI.
🔊
TTS / STT Degradation
If ElevenLabs API fails → UI shows error, text response still displayed. If browser doesn't support Web Speech API → microphone button hidden gracefully.
🛡️ All API endpoints return consistent error objects: {"error": "message"} with appropriate HTTP status codes (400/401/403/500). Frontend displays user-friendly messages.

// Header (base64url) { "alg": "HS256", "typ": "JWT" } // Payload (base64url) { "uid": "uuid-here", "email": "user@example.com", "name": "John Doe", "role": "user", "iat": 1716890400, "exp": 1717495200 // +7 days } // Signature (HMAC-SHA256) HMAC(base64(header) + "." + base64(payload), JWT_SECRET)
🔐
Stateless Authentication
No session store needed. Server only needs the JWT_SECRET to verify any token. Scales horizontally without shared state.
👑
Role-Based Access
`role` claim in payload gates admin routes. requireAdmin middleware checks role === 'admin' after requireAuth verification.
💾
Client-Side Storage
Token stored in localStorage as 'chatbot_token'. AuthContext reads it on app load, auto-refreshes user state. 7-day expiry for session continuity.

WAL (Write-Ahead Logging) Benefits

Design Patterns

Architectural Design Patterns

🏛
Client-Server (3-Tier)
React frontend (presentation) ↔ Express API (logic) ↔ SQLite (data). Clean separation enables independent deployment and scaling of each tier.
🔗
REST (Stateless API)
All server interactions via HTTP verbs on resource URIs. Stateless requests enable horizontal scaling. JWT replaces session state entirely.
🧩
RAG (Retrieval-Augmented Generation)
Domain knowledge retrieved at query time and injected into LLM context. Eliminates hallucination risk for factual domain questions.
🔐
Middleware Chain (AOP)
Cross-cutting concerns (auth, CORS, body parsing) separated into Express middleware. Business logic stays clean. Aspect-oriented separation.
🏭
Multi-Tenant (Process Isolation)
Separate OS processes per instance, each with isolated SQLite file. True data isolation without containers or VMs.
🎯
Strategy Pattern (Knowledge Sources)
RAG, own knowledge, and web search are independently togglable strategies with configurable weight percentages. Compose any combination.

API Principles

REST API Design Principles

📐
Resource-Oriented URLs
URLs identify resources: /api/conversations/:id, /api/user/memories/:id. Actions expressed via HTTP verbs (GET/POST/PUT/PATCH/DELETE).
🔄
Consistent Response Shape
Success: data payload. Error: {"error": "message"} with appropriate HTTP status (400/401/403/500). Frontend handles both shapes uniformly.
🔗
Stateless Requests
Every request carries full auth context (JWT Bearer token). No server session required. Enables load balancing without sticky sessions.
🏷️
Content Negotiation
JSON for all API responses. MP3 audio for /api/tts. Content-Type headers set correctly on all responses for client-side handling.
